# Chronicle UI Redesign Plan

## UI Technology and Architecture 
Chronicle’s UI is built with **SwiftUI** for all app interfaces, integrated with **AppKit** for menubar and window management. The app uses an `NSStatusBar` **status item** (menubar icon) and an `NSPopover` to present a SwiftUI `ContentView` for quick access. Separate SwiftUI views are embedded in **NSWindowController** instances for the **Statistics dashboard** and **Preferences** windows. This hybrid approach leverages SwiftUI for declarative UI while using AppKit (`NSApplicationDelegate`, `NSHostingController`, etc.) to manage the menubar icon, popover, and additional windows. There are no Storyboards – all UI is code-driven. The target platform is **macOS (Apple Silicon)**, and the app will fully support both light and dark modes using system colors and adaptive SwiftUI views.

SwiftUI scene structure is minimal: the `@main` `ChronicleApp` sets an **accessory** (no-dock) app and defers UI setup to `AppDelegate`. We will continue with this approach, refining it with modern SwiftUI where appropriate (e.g. using `NavigationSplitView` for sidebars as already done in the dashboard). We will not introduce third-party UI frameworks; the plan uses **native SwiftUI components** and SF Symbols for icons to align with macOS design guidelines.

## Key Data and Service Layers 
The frontend will interface with existing backend singleton services and models, ensuring we reuse the mature logic:
- **`AppState` (ObservableObject):** Holds user preferences and UI state (selected date, filters, toggles) and syncs with `UserDefaults`. The UI will bind to `AppState.shared` for live updates (e.g. toggling tracking settings, idle settings, filters).
- **Activity Tracking Services:** `ActivityTracker` (records app usage sessions) and related services emit notifications (`didRecordSessionNotification`) that the UI listens for to refresh data in real-time.
- **`DatabaseService`:** Provides CRUD operations for activities, tags, rules, markers (point + interval sessions), and app mappings. UI components (timeline, tag editor, app mapping list, etc.) call this service to fetch or update persistent data.
- **`AggregationService`:** Computes aggregated stats (summaries, top apps/tags, timeline items) for a given time range and filter. The Stats views rely on this for generating summary metrics, top lists, and chart data.
- **`ReportService` and `ReportSettings`:** Manage export generation and scheduling. The UI will present controls for export settings (destination folders, templates, enable/disable auto-export) and use `ReportService` to trigger manual exports (e.g. “Export Now” or generating a report on demand). `ReportSettings.shared` (ObservableObject) stores auto-export toggles, last exported dates, and folder bookmarks – the settings UI will bind to these for live updates.
- **Localization and Utilities:** `AppLanguageManager` for dynamic language switching (with published `currentLanguage`), and utilities like `ColorHex` (to convert hex to Color) support theming. We will ensure any text uses localized `StringKey` entries (`L("key")` or `LocalizedStringKey`) so the UI remains multilingual. 

These layers mean the **UI can remain thin**: we’ll primarily call service methods or bind to published properties rather than duplicating logic. For example, adding a tag calls `DatabaseService.insertTag` and auto-exports run via `ReportService.autoExportIfNeeded`.

## Existing Views vs. New UI Requirements 
Chronicle’s repository already contains many SwiftUI views, but they are currently **raw and lack styling or clear navigation**. We will refine and extend these as follows:

- **Menubar Popover View (`ContentView`):** Exists – shows a basic vertical stack with app title and a segmented control for “Timeline” and “Stats”, embedding `TimelineView` and `StatsView`. We will polish this view (spacing, alignment, styling) but it remains the quick-glance UI. The menubar popover will default to the Timeline tab, giving an overview of today’s activity, with the option to switch to Stats.
- **Timeline Views:** Exists – `TimelineView` (for popover) and `DashboardTimelineView` (for main window) list recorded app sessions and markers. These already include date navigation (today/prev/next), filtering by tag/app, and an idle toggle. We will ensure consistent styling (using our design system for spacing and fonts) and possibly unify features between popover and full-window timeline. The main timeline will remain scrollable with grouping by hour or marker, and the menubar timeline may be simplified for brevity. Markers now include **point notes** and **interval sessions**; the popover provides a quick entry control and the dashboard has read-only lists (Notes / Sessions).
- **Stats Views:** Exists – `StatsView` (popover) and `DashboardStatsView` (main window) show usage summary and top apps/tags. We’ll refine layout and make sure the main Statistics panel is comprehensive:
  - The **Overview** section will present high-level summaries (total active time, idle time, etc.) for the selected range and possibly comparisons (e.g. today vs last 7 days vs 30 days) as cards.
  - **“By App” and “By Tag” breakdowns** will list usage per app or tag. In code, the overview mode in `DashboardOverviewView` already provides an **interactive chart** (Gantt chart for top apps or tags over time). We will leverage this to fulfill the “Trends” requirement: users can toggle between Apps or Tags mode and Day or Week scope to see visual usage patterns. Additionally, we might introduce simpler list views or sortable tables for all apps or tags if needed (e.g. a scrollable list of all apps with time, not just top 10).
  - A **Trends chart** is essentially covered by the existing GanttChartView in Overview. We will ensure this is accessible and polished. If needed, we can incorporate SwiftUI’s `Chart` for simpler time-series (for example, a line chart of total hours per day) to complement the Gantt chart.
- **Dashboard Main Window (`DashboardView` & subviews):** Exists – currently contains a NavigationSplitView with sidebar sections: *Timeline, Overview, Stats, Reports, Apps, Tags & Rules, Markers* (and Debug in dev mode). This “dashboard” consolidates both **statistics** and some **configuration** pages. In the redesign, we will streamline the main window to focus on **data views (analytics)**, and move configuration into the Preferences window:
  - The main **Statistics window** will include Timeline, Overview, Stats, Markers (and possibly a combined “Details” section for per-app or per-tag lists if required). These are the panels for data analysis.
  - We plan to **remove or de-emphasize the config sections (Apps mapping, Tags/Rules, Reports)** from the main dashboard, to avoid confusion. Those will live in Settings. (The code’s reuse of `AppMappingsView` and `TagsRulesView` in both places can be refactored so that the sidebar in the main window no longer lists them for normal users.)
- **Preferences/Settings Window (`PreferencesView` & tabs):** Exists – currently uses a TabView with tabs: General, Apps, Tags & Rules, Privacy. We will **restructure this into a sidebar-style preferences panel** for better scalability:
  - **General:** (Exists as `GeneralPreferencesView`) containing basic toggles (Launch at login, ignore self, language picker, idle detection and tracking settings, etc.). We will polish grouping (the existing code uses GroupBoxes for Idle and Tracking Quality settings which we’ll keep) and ensure controls write to `AppState` (already wired).
  - **Tags:** This will encompass tag management and app tag mappings. We may split it into two subsections or combine them in one view with sub-segment:
    - *Tag Management:* Create, edit, delete tags and choose tag colors (already implemented via `TagsManagementView` in the Tags & Rules tab).
    - *App Tag Mapping:* List of detected applications with their assigned tag, with search and filter (implemented in `AppMappingsView`). This allows overriding the default tag inference on a per-app basis.
    - We might keep these sub-views under a segmented control “Tags | Apps” within the Tags section (similar to how current `TagsRulesView` uses a Picker for Tags vs Rules). Alternatively, we could make **Tags** and **Apps** two separate sections in the sidebar. However, since the user story suggests “Tags: override tag mappings for apps”, we interpret that as a single combined section for tag configuration. Our plan is to include both functionalities in the Tags section, using internal segmentation if needed to organize the UI.
  - **Export:** A new Preferences section dedicated to report export settings. We will surface scheduling options and output configuration here:
    - Choose export folders for daily/weekly reports and CSV (with “Choose Folder” dialogs, using the security-scoped bookmarks in `ReportSettings`).
    - Toggles to enable/disable **daily and weekly auto-export** and whether to overwrite existing files.
    - Possibly editing the report templates text (the code already has TextEditors for daily/weekly template in `DashboardReportsView`). We’ll include those so users can customize report content.
    - Display last export run info (e.g. “Last daily export: today at 00:00” based on `ReportSettings.lastExportedDay`) and next scheduled run (implicitly next day/week if auto-enabled).
    - A manual “Export Now” button (or “Generate Report”) to trigger an immediate export for the current day/week or a selectable range. (This duplicates the functionality of “Generate for Selected Day/Today” buttons in the code’s reports view.)
    - We will reuse much of `DashboardReportsView` logic here, repackaged under Settings.
  - **Privacy/Data:** We will retain the Privacy section (currently in TabView) to allow opening the data folder and wiping data. This includes the database path display and a “Wipe Data” action with confirmation alert. It’s a smaller section but important for transparency. We might rename it to **Data & Privacy** and include any related settings (window title capture now requires Accessibility permission and is optional).
  - **Advanced/Debug (Optional):** In debug builds, a section or toggle for enabling verbose logging exists in General. We’ll keep such debug UIs either within General or a hidden Debug section.

The Preferences window will thus have a sidebar list of sections: *General, Tags, Export, Privacy* (and possibly *Advanced* in debug). Selecting a section shows the corresponding form. This replaces the current icon-tab style with a more standard sidebar navigation, improving scalability and clarity.

## App-Wide Navigation Structure 
**Menubar Primary Entry:** The app runs primarily in the menubar (no Dock icon). The menubar **clock icon** serves as the hub:
- **Left-click** on the icon toggles the Chronicle popover, showing the quick dashboard (timeline/stats).
- **Right-click** (or Option-click) opens a context menu with key actions:
  - **“Open Statistics”** – opens the main Statistics window (formerly called “Dashboard”) for detailed views. This will bring forward the NavigationSplitView interface where users can navigate Timeline, Overview, etc., in a resizable window.
  - **“Open Settings”** – opens the Preferences window for configuration.
  - **“Export Now”** – manually triggers an immediate export of data. We will connect this to `ReportService.exportCSV` or generate a daily report on demand. A brief notification or log entry can confirm success/failure.
  - **“Quit Chronicle”** – terminates the app (existing functionality).
These menu items will be implemented by extending the current `NSStatusItem` menu setup in `AppDelegate` (which already has Open Dashboard, Preferences, Quit; we will add “Export Now” and adjust naming).

**In-App Navigation:** Once a window is open:
- The **Statistics main window** (Dashboard) uses a persistent **sidebar** (via `NavigationSplitView`) on the left and a detail area on the right. The sidebar lists sections (Timeline, Overview, etc.). Switching sections updates the detail view accordingly. This allows quick switching between different statistical views without opening new windows. A toolbar gear button (already in `DashboardView`) provides another entry point to Preferences.
- The **Preferences window** will have its own sidebar (using a `List` or `SidebarListStyle`) with sections as described. Selecting an item (General, Tags, Export, Privacy) will display that settings form on the right. This window is separate and can stay open alongside the main window or popover.
- The **Popover** itself contains a mini navigation: a segmented control for Timeline/Stats as implemented. There is no further navigation within the popover – it’s meant for quick access. For deeper exploration, the user will use the “Open Statistics” window.

This structure ensures a clear separation: **menubar popover for quick view**, **main window for in-depth analytics**, and **settings window for configuration**. Users can easily switch contexts: e.g., from the popover they click “Open Statistics” for more details, or hit the gear icon to adjust settings.

## Menubar Popover UI Flow 
When the user clicks the menubar icon (the small clock symbol):
1. **Popover Appears:** showing the **Timeline** by default (today’s timeline of activity). The header shows the app name and possibly today’s date, and the content scrolls through chronological usage with any markers inserted. The user can scroll within the popover to review recent activity.
2. The top of the popover has a **segmented control** (Timeline | Stats). Selecting “Stats” switches the popover content to a summary view:
   - Stats in popover will show a concise summary for today (total time, active vs idle, number of sessions or top app). The existing `StatsView` already provides Summary, Top Apps, Top Tags, etc., which we may include partially (likely the summary cards and maybe top 3 apps/tags in a compact form). This gives the user a quick glimpse without opening the full window.
   - Both Timeline and Stats popover views include small navigation controls: the date picker or “Today” button and left/right arrows to move the day, as seen in code. These will remain, allowing quick checks of yesterday or another date from the menubar directly.
3. **Closing Popover:** Clicking the icon again or outside closes it. The state of the popover (last selected tab, last viewed date) can persist via AppState so that reopening the popover restores where you left off (for convenience).
4. **Right-Click Menu:** If the user right-clicks the icon instead, the popover will not show. Instead, the context menu appears with the items mentioned (Open Statistics, Open Settings, Export Now, Quit). Choosing an item triggers the respective action:
   - *Open Statistics:* If the Statistics window isn’t open, it will be initialized and shown; if it is already open (but maybe behind other windows), it will be brought to front (using `NSApp.activate` and `makeKeyAndOrderFront`). We will also ensure that the Statistics window’s title and content are up-to-date (the code already updates the window title via localization on language changes).
   - *Open Settings:* Similar behavior for Preferences window. We use the singleton `PreferencesWindowController.shared.show()` which either creates the window (embedding the Preferences SwiftUI view) or focuses it if already created.
   - *Export Now:* We will implement an `@objc` handler in AppDelegate (or a small helper function) that calls `ReportService` to perform an export. For example, it could generate the daily report for today immediately. On success or failure, we might provide user feedback. Since this is a quick action, a subtle approach is to momentarily show the popover with a status message, or simply log it. In a future polish, we could integrate macOS notifications for “Export completed” – but initially a simple confirmation text in the menu or console log (as `AppLogger`) may suffice.
   - *Quit:* Immediately terminates as usual.

This menubar-centric flow ensures the app is readily accessible without cluttering the screen, and more intensive tasks neatly transition to dedicated windows.

## Key UI Components and Elements 
We will leverage or create a set of reusable components following a design system:
- **Header Text:** Many screens have a title (e.g. “Timeline”, “Stats”, “Tags & Rules”) at the top. We will use consistent styling for these section headers. For instance, use `.title2.weight(.semibold)` for page titles (as already used in code), ensuring a unified look.
- **Cards and GroupBoxes:** The app uses **GroupBox** in several places (Stats summary, Top lists, export sections) to visually group content with a subtle container. We will continue using GroupBoxes for grouping and possibly introduce **rounded rectangle cards** for summary metrics. E.g., the **SummaryCard** component in Stats (small rounded rectangle with a value) will be part of our design language for key metrics. All cards will use a uniform corner radius and background color (likely `Color(nsColor: .controlBackgroundColor)` or a custom semantic color for cards) for consistency.
- **Lists and Rows:** Data lists such as the timeline entries, markers list, app mapping list, top apps/tags list, etc., will use either `List` with `ForEach` or `LazyVStack` inside a ScrollView, depending on performance needs. Many of these are custom because they intermix types (activities and markers) or have rich layouts (like icons, progress bars, etc.). We will ensure each row type is visually distinct but coherent:
  - *TimelineRowView*, *MarkerRowView*, and *MarkerSpanRowView* handle displaying app sessions, point markers, and interval sessions respectively. We’ll refine spacing and maybe truncate long titles to avoid overflow. Idle sessions could be greyed out (as currently).
  - *TopAppRow* and *TopTagRow* in Stats show a small icon or color dot and a progress bar indicating percentage. These already align with our intended design; we will just ensure consistent spacing (using standard spacing values) and perhaps improve how the progress is visualized (the code uses `ProgressView` which is fine).
  - *AppMappingRowView:* (within AppMappingsView) likely includes a dropdown (Picker) for tag selection per app. We’ll ensure the row is clearly separated, maybe using a slight background on hover or alternate rows for readability if the list is long.
  - *TagEditorRow* and *RuleEditorRow:* in the Tags & Rules section provide inline text fields and buttons for editing tag name/color and rule details. These are essentially mini-forms inside list rows. We will make sure the controls (textfields, steppers, pickers) use standard control sizes and are aligned. We might wrap rule rows in a rounded rectangle background to distinguish them, as the code already does for RuleEditorRow (padding and background).
- **Forms and Controls:** The Settings sections are forms with toggles, pickers, sliders, steppers, and text fields:
  - We will align labels and controls in vertical stacks for a clean look (the code uses `VStack` inside `GroupBox` for sections like “Idle Detection” or “Tracking Quality”). We’ll maintain a spacing of ~8-12 points between form rows.
  - **Toggles**: Use default SwiftUI Toggle with `.switch` style for macOS (already in use). We’ll include descriptive text below toggles when needed (the code often puts a `Text(...).font(.caption)` below a Toggle to explain it).
  - **Pickers/Dropdowns**: Used for language selection, tag selection in rules, and possibly for any dropdown fields. We will use `.pickerStyle(Segmented)` for small sets (e.g., language, range mode, etc.) and pop-up button style for longer lists (default for Picker in macOS).
  - **Sliders/Steppers**: Already used for idle timeout (slider) and numeric settings (steppers for durations). We’ll group the label, slider, and stepper together with consistent spacing and ensure the value is displayed (as currently “\(appState.idleThresholdSeconds)s” etc.).
  - **Buttons**: We use prominent bordered buttons for primary actions (e.g., “Add”, “Export CSV”, “Generate Today”), and plain or bordered for secondary (e.g., “Reset to Default”, “Delete”). We will apply `.buttonStyle(.borderedProminent)` for primary actions to make them stand out in our forms (as code does in some cases). We will also be mindful of using `.tint(.red)` for destructive actions like “Wipe Data” or “Delete Tag” so the user recognizes them.
  - **Modals**: The “Wipe Data” alert and any critical confirmation will be presented with clear messaging and a destructive-style confirmation button.
- **Charts and Visualizations:** The **Overview’s GanttChartView** is a custom component for visualizing usage over time (with horizontal bars). We will keep this as it provides a powerful visual overview. We’ll ensure its legend and axes (TimeGridView for hour ticks) are properly styled (likely already fine, showing hour labels). If time permits or needed, we might add a simpler chart for trends, but the existing coverage is likely sufficient.
- **Miscellaneous UI elements:** 
  - **Icons:** We will use SF Symbols for all icons (menubar icon “clock”, section icons in sidebars, and any button icons like the gear for settings or arrows for navigation). Using consistent SF Symbol weights (likely medium) and rendering modes (template vs multicolor as appropriate) will ensure a cohesive look.
  - **Text Selection and Copy:** For certain informational text (like database path in Privacy), the code uses `.textSelection(.enabled)`. We’ll continue to enable text copying where it benefits the user.
  - **Scroll Indicators:** We expect long content (timeline, lists) to be scrollable. By default, SwiftUI on Mac shows scroll bars. We’ll ensure our padding doesn’t cut them off and consider using `.scrollContentBackground(.hidden)` if needed to match design (for example, in a sidebar list).

## Design System and Styling 
We will introduce a simple design system to ensure consistency:
- **Color Palette:** We will use semantic colors (wrapping system colors) rather than hard-coded hex values for UI chrome. For example, use `Color.primary`/`secondary` for text, `Color(nsColor: .windowBackgroundColor)` or `.controlBackgroundColor` for card backgrounds, and accent color from the asset catalog or system accent. We’ll define a `ThemeColors` struct or extension with static properties for key colors, e.g.:
  - `ThemeColors.background` (perhaps using system grouped background),
  - `ThemeColors.cardBackground` (if we need a slightly elevated background, could use system secondary background),
  - `ThemeColors.primaryText` (likely default),
  - `ThemeColors.secondaryText` (default secondary).
  This approach makes it easy to adjust one place if needed (for dark mode tweaks) and avoids magic numbers in views.
- **Typography:** We will rely on SwiftUI’s dynamic type sizes and weights to keep text legible. However, we’ll document standard usage:
  - Titles (section headers) use `.title2` or `.headline.bold()`,
  - Subsection headers (within a card or group, e.g. “Top Apps”) use `.headline` or `.subheadline.weight(.medium)`,
  - Body text uses `.body` or `.callout` as appropriate,
  - Captions (for helper text or footnotes, and value labels) use `.caption` or `.caption2` for very small.
  We’ll ensure these are used consistently (the code already uses many `.caption` for descriptions and `.headline` for group titles, which we will continue).
- **Spacing and Layout:** We will define consistent spacing values:
  - Use base spacing units of 4pt or 8pt increments. For instance, small gaps 4–6 pt, standard gaps 8–12 pt, larger padding 16–20 pt. In code, we see a lot of `.padding(20)` or `.padding(16)` and spacing of 12 in VStacks – we will rationalize these to a set of constants (e.g. `Metrics.padding` could be 16 for general padding, `Metrics.sectionSpacing` = 12, etc.). We might create a small `Metrics` struct with static let values (XS, SM, MD, LG) to avoid magic numbers.
  - **Margins/Padding:** All view containers will have a consistent padding at edges (likely 16 or 20 points in the popover and main content as already set). We will apply a minimum padding of, say, 20 on window content to avoid elements touching edges.
  - **Corner Radius:** We will apply a uniform corner radius to all rounded elements (cards, popover backgrounds, etc.). Likely use 6 or 8pt radius for cards and popover, and maybe 4pt for small inner elements. The code uses 8 for SummaryCard and 3 for tiny color swatches – we can allow two scales (small radius ~4 for small UI elements, medium radius ~8 for containers). We’ll avoid overly-rounded corners to stay in line with macOS aesthetic.
  - **Shadows and Effects:** macOS light mode doesn’t use heavy shadows. We might give popover or menu a slight shadow if not provided by system. For custom components (like Gantt bars), the design already uses subtle strokes on hover. We will maintain those. We won’t introduce large shadows, to keep the design clean and native.
- **Dark Mode:** All colors chosen will be tested in dark mode. By using system colors (which automatically adapt) and SF Symbols (which have both light/dark rendering), we ensure high contrast. For any custom color (like tag colors), we’ll test their appearance against dark backgrounds (the tag color palette might need some adjustments for dark mode, e.g. the overlay stroke uses opacity to remain visible on dark). Our design tokens approach means if a custom background color doesn’t look right in dark mode, we can adjust it in one place.
- **State Indications:** We will use visual cues for interactive elements:
  - Hover effects on clickable list rows (like the Gantt chart rows highlight on hover, we might do similar for app mapping rows using `.onHover` to show a light background).
  - Selection highlighting in sidebar (NavigationSplitView handles this with accent color).
  - Disabled state dimming (SwiftUI auto-dims disabled controls, which we’ll utilize, e.g. a “Today” button is .disabled when already on today).
  - Error messages in UI (e.g., last DB error or export error) shown in red `.foregroundColor(.red)` caption text, as currently done.

Overall, this design system will be documented in code comments and consistently applied to avoid any “raw” or inconsistent look.

## Implementation Priorities and Roadmap

We’ll ensure each setting binds to `AppState` or `ReportSettings` so changes persist. By the end of this phase, the Preferences panel will be fully functional with a modern navigational structure.

   - Introduce a `Constants` or `Design` struct in SwiftUI (perhaps in a new file `DesignSystem.swift`) that defines colors, spacing, etc. Refactor views to use these (e.g., replace literal `.padding(16)` with `.padding(Design.spacing)` if we set `spacing = 16` for general padding).
   - Ensure color usage is audited: use `Color.primary/secondary` or our `DesignColors` instead of fixed .gray or .blue (except where intentionally using tag colors). This will ensure adaptability and a professional, consistent look.
   - Check all fonts and align them with the intended size hierarchy. If any view uses a magic font size, replace with a system style or a relative size.
   - Check interactive states (hover, selection) and ensure they use system defaults or defined styles.
   - This phase is about visual consistency and maintainability, not adding features.
7. **UI Testing (Phase 7):** Add SwiftUI UI tests and unit tests for critical UI logic:
   - For example, a UI test that launches the app, opens the menubar popover, toggles to Stats and verifies a UI element (like the presence of “Total” text in summary).

   - Tests will focus on things like “Add Tag flow adds a new tag entry”, “Changing app mapping updates timeline filter results”, “Export Now triggers file creation (we can stub ReportService in tests)”.
   - We will keep tests lightweight and avoid flakiness – focusing on the logic and binding rather than actual rendering (since SwiftUI’s UI tests might require running the app).
8. **Final Polish (Phase 8):** In the last phase we will address any remaining UI inconsistencies and quality issues:
   - Ensure windows behave well: resizing the Statistics window keeps layout (the NavigationSplitView already handles min sizes; we may adjust any `.frame(width: ...)` constraints if needed to allow flexibility).
